\hypertarget{purpose}{%
\section{Purpose}\label{purpose}}

This is the Design Document (DD) of ROAd (Robotaxi Optimized
Allocation). The document describes how the system is built: the
software architecture, the components and their interfaces, the way they
interact at runtime, the design patterns we adopt, the user interface,
the mapping from requirements to design, and the plan to implement,
integrate and test the system.

\hypertarget{main-goals}{%
\subsection*{Main Goals}\label{main-goals}}
\addcontentsline{toc}{subsection}{Main Goals}

ROAd supports the management of an autonomous taxi fleet in a city.
Passengers can request immediate rides or book rides in advance from a
mobile app; the system assigns a suitable robotaxi according to a
vehicle-allocation strategy that the fleet operator can choose at
runtime. The system tracks the lifecycle of each robotaxi, notifies
passengers about relevant events, lets the operator monitor the fleet
from a web dashboard, and proactively rebalances available robotaxis
toward areas of expected high demand. Autonomous driving and onboard vehicle control are outside the scope of
ROAd. Geocoding, mapping, and route computation rely on external services
and are not implemented by the core system. Payment processing is also
outside the project scope and is not integrated into the prototype.

\hypertarget{definitions}{%
\subsection*{Definitions}\label{definitions}}
\addcontentsline{toc}{subsection}{Definitions}

\begin{itemize}
\tightlist
\item
  \textbf{Component}: A modular, replaceable unit of the system that
  provides and requires services through well-defined interfaces.
\item
  \textbf{Tier}: A physical (deployment) layer of the architecture. ROAd
  is organised in three tiers: presentation, application, data.
\item
  \textbf{S2B - Software To Be}: The ROAd backend together with the
  two clients.
\item
  \textbf{Manager}: An internal backend component responsible for one
  coherent area of the application logic.
\item
  \textbf{Gateway}: A component that mediates access to an external
  system, hiding its specific protocol from the rest of the system.
\item
  \textbf{Context}: In the State/Strategy patterns, the object that
  delegates part of its behaviour to a separate state/strategy object.
\end{itemize}

\hypertarget{architectural-design}{%
\chapter{Architectural Design}\label{architectural-design}}

\hypertarget{overview-and-architectural-style}{%
\section{Overview and architectural
style}\label{overview-and-architectural-style}}

ROAd adopts a \textbf{three-tier client-server architecture}:

\begin{itemize}
\tightlist
\item
  A \textbf{presentation tier} with two thin clients:

  \begin{enumerate}
  \def\labelenumi{\arabic{enumi}.}
  \tightlist
  \item
    The Passenger mobile-friendly web application
  \item
    The Operator Web Dashboard
  \end{enumerate}
\item
  An \textbf{application tier} for the ROAd backend (the S2B core),
  which contains all the management logic, organised as a set of
  cooperating components behind an API Gateway.
\item
  A \textbf{data tier} for a single relational database that stores
  accounts, requests, rides, vehicles and reservations.
\end{itemize}

\hypertarget{component-view}{%
\section{Component view}\label{component-view}}
The main components and the operations they export are:

\begin{itemize}

\item
  \textbf{API Gateway}: Single entry point for the clients.
  Exposes REST endpoints and a WebSocket notification channel,
  routes requests to the appropriate components, and enforces
  authentication and role-based access.

\item
  \textbf{AuthenticationManager}: Exposes \code{authenticate()},
  \code{register()}, and \code{updateProfile()}.
  Manages user accounts and issues signed access tokens (R1, R2).
  \textbf{[v1.1]} Public registration creates Passenger accounts;
  Operator accounts are provisioned separately.

\item
  \textbf{RideRequestManager}: Exposes \code{submitImmediate()},
  \code{submitAdvance()}, and \code{cancel()}.
  Validates requests and coordinates allocation, reservations,
  and cancellation through the fleet, allocation, persistence,
  and external-service interfaces (R3, R4, R14).
  \textbf{[v1.2]} A second port exposes
  \code{AdvanceBookingActivator.runOnce()} to activate bookings whose activation time has been reached.
  \textbf{[v1.3]} The \code{IRideLifecycleService} port exposes
  \code{startPickupNavigation()}, \code{pickupReached()},
  \code{startRide()}, and \code{completeRide()}.
  The component manages Ride persistence and status changes,
  coordinating vehicle transitions and notifications.
  \textbf{[v1.5]} The \code{IFleetTelemetryService} port reads
  vehicle telemetry, forwards observed positions to
  \code{FleetMonitor}, and advances the ride lifecycle.

\item
  \textbf{AllocationManager}: Exposes
  \code{allocate(request, candidates)} and
  \code{setActiveStrategy()}.
  Acts as the Strategy context, selecting an eligible robotaxi
  through the active allocation policy (R5, R8).
  \textbf{[v1.1]} Provides \code{getActiveStrategy()} and accepts
  the strategy name and change source when updating the policy.
  A manual selection atomically updates both the strategy and
  the control mode.

\item
  \textbf{ModeController}: Exposes \code{onTrafficLevel()},
  \code{setManual()}, and \code{enableAuto()}.
  Coordinates Auto/Manual mode and traffic-driven strategy
  switching, preserving manual overrides (R12, R13, NFR9, NFR10).
  \textbf{[v1.1]} Provides \code{getMode()} and immediately
  re-evaluates the last known traffic level when Auto Mode is enabled.
  \textbf{[v1.4]} A second port exposes
  \code{TrafficMonitor.runOnce()} to acquire traffic readings.
  \textbf{[v1.10]} \code{getMode()} also returns the last observed
  traffic level.

\item
  \textbf{FleetMonitor}: Exposes \code{getCandidates()},
  \code{getAvailableRobotaxis()}, \code{getFleetStatus()},
  \code{assign()}, and \code{requestRebalancing()}.
  Maintains vehicle position and state information and coordinates
  lifecycle transitions through the State pattern (R7, G6, G8).
  \textbf{[v1.2]} Adds \code{getBookableRobotaxis()} for future
  reservations and \code{releaseAssignment()} for cancellation.
  \textbf{[v1.3]} Exposes \code{startPickupNavigation()},
  \code{pickupReached()}, \code{startRide()}, and
  \code{completeRide()}.
  \textbf{[v1.5]} Adds \code{recordPositions()} and
  \code{completeRebalancing()}.
  \textbf{[v1.8]} Rebalancing completion updates the target
  \code{zoneId} together with the transition to \code{AVAILABLE}.

\item
  \textbf{RebalancingManager}: Exposes \code{analyzeDemand()}
  and \code{rebalance()}.
  Estimates zone demand and automatically repositions idle
  robotaxis from surplus zones toward zones with unmet demand
  (R10, R11, G9).
  \textbf{[v1.4]} Reads historical demand and active events through
  \code{IPersistenceService} and records repositioning actions
  in \code{rebalancing\_action}.
  \textbf{[v1.5]} Sends route commands through
  \code{ExternalServicesGateway}.
  \textbf{[v1.8]} Exposes \code{completeArrivedRebalancing()}
  to check arrivals independently of the planning cycle and
  request completion from \code{FleetMonitor}.

\item
  \textbf{MaintenanceManager}: Exposes
  \code{requestMaintenance()} and \code{completeMaintenance()}.
  Manages maintenance records and the corresponding vehicle
  transitions through the State pattern, excluding vehicles
  under maintenance from allocation (R9).
  \textbf{[v1.3]} Publishes notifications after maintenance
  state changes have been persisted.

\item
  \textbf{NotificationManager}: Exposes \code{update(event)}.
  Acts as the concrete Observer and dispatches domain events
  to the relevant Passenger and Operator sessions (R6, G7).
  \textbf{[v1.3]} A second port exposes
  \code{registerSession(session)}, \code{removeSession(session)},
  and \code{registeredSessions()} to manage active connections.
  \textbf{[v1.12]} Persists operator alerts and exposes
  \code{recentAlerts(limit)} through a third port, allowing
  the dashboard to retrieve recent alerts after a reload.

\item
  \textbf{PersistenceManager}: Exposes \code{create()},
  \code{update()}, \code{filterAvailable()}, and \code{reserve()}.
  Provides database access, availability filtering, and atomic
  reservation operations, including joint creation of an advance
  booking and its reservation. Database constraints prevent
  overlapping vehicle reservations (NFR4, C1).
  \textbf{[v1.1]} Exposes \code{find()} for querying persisted data.

\item
  \textbf{ExternalServicesGateway}: Exposes \code{getETA()}
  and mediates communication with external providers (NFR8).
  \textbf{[v1.4]} Uses a facade with provider-specific adapters
  and exposes \code{getTraffic()}.
  \textbf{[v1.5]} Adds \code{commandRoute()} and
  \code{readTelemetry()} for fleet interaction.
  A separate \code{FleetSimulationPort} advances the simulated
  vehicles used by the prototype.
  \textbf{[v1.11]} Supports configurable hourly and scripted
  traffic adapters, with the hourly source as the default.

\end{itemize}

\subsubsection{Client access and API routing}

Figure~\ref{fig:components-client-access} shows how the passenger and
operator clients access the system through the interfaces exposed by the
\code{APIGateway}. The gateway acts as the entry point of the backend
and routes each request to the service responsible for the requested

\hypertarget{allocationmanager-strategy}{%
\subsection{AllocationManager}\label{allocationmanager-strategy}}

Figure~\ref{fig:class_allocation} shows the classes implementing the
allocation logic.The
\code{AllocationManager} maintains a registry of
\code{AllocationStrategy} implementations and delegates vehicle
selection to the strategy identified by the active strategy name. The
concrete strategies \code{NearestAvailableStrategy} and
\code{MinimumETAStrategy} implement the available allocation policies,

\textbf{{[}v1.1{]}} The \code{allocate()} and
\code{selectRobotaxi()} operations may return no vehicle when no

manual mode control. Candidate ties are resolved deterministically by
\code{robotaxiID}, while candidates whose score cannot be computed are
excluded.
\textbf{{[}v1.4{]}} The \code{ModeController} governs the automatic and
manual allocation modes and the current traffic level. These values are
persisted in the shared \code{system\_mode} record rather than kept as
local object state, ensuring consistency across replicated backend
instances.\\
The allocation strategies expose a common interface. Strategies that
require external information, such as
\code{MinimumETAStrategy}, obtain it through the
\code{ExternalServicesGateway}; this interaction is asynchronous, while
the common strategy interface remains unchanged.

\hypertarget{notificationmanager-observer}{%
\subsection{NotificationManager}\label{notificationmanager-observer}}

Figure~\ref{fig:class_notification} shows the notification classes. \code{Robotaxi} and
\code{Ride} are subjects, while the \code{NotificationManager} is
the observer that is notified whenever a subject changes state. It then
dispatches the received events to the \code{PassengerAppSession} and
the \code{OperatorDashboardSession}.

\ddfigure{diagrams/class_diagrams/class_notification}{Class diagram of the notification mechanism. The Observer pattern used
to propagate domain events from subjects to observers.}{fig:class_notification}
\noindent
\textbf{Realisation of the two subscription levels {[}v1.1{]}.}
The diagram represents two distinct one-to-many relations with different
lifetimes.
\begin{itemize}
    \item The relation between \code{Subject} and \code{Observer} is static during
the execution of an operation. \code{Robotaxi} and \code{Ride} are
reconstructed from the persisted data when needed and temporarily hold
the registered \code{NotificationManager}. After a state or ride-status
change has been successfully persisted, the subject notifies this
observer.
\item The relation between \code{NotificationManager} and the client sessions
is dynamic. \code{PassengerAppSession} and
\code{OperatorDashboardSession} are created when a WebSocket connection
is established and removed when it is closed. Passenger sessions receive
events related to their own rides, whereas operator sessions receive
fleet-wide events. Domain objects therefore remain independent of the
transport layer.

\end{itemize}
\textbf{Notification timing {[}v1.3{]}.}
Notifications are emitted only after the corresponding transition has
been persisted successfully. \code{FleetMonitor} notifies observers of
robotaxi state changes, while \code{RideRequestManager} notifies them of
ride-status changes. This prevents clients from receiving notifications
for transitions rejected by the persistence layer.\\
\textbf{Ride as a second subject {[}v1.3{]}.}
In addition to \code{Robotaxi}, \code{Ride} acts as a subject and
notifies the \code{NotificationManager} whenever its status changes.
This supports passenger notifications throughout the ride lifecycle.\\
\textbf{Persistent operator alerts {[}v1.12{]}.}
Passenger notifications and operator alerts are handled separately.
Passenger notifications are stored for their intended recipient, while
fleet-wide governance events are persisted as operator alerts.
The \code{recentAlerts()} operation allows the operator dashboard to
retrieve these alerts after a disconnection or page reload.

\noindent
\textbf{Traffic hysteresis rule {[}v1.1{]}.}
In Auto Mode, \code{ModeController} evaluates the last observed traffic
level according to the following rule:

\begin{longtable}[]{@{}ll@{}}
\toprule\noalign{}
Observed level & Effect in Auto Mode \\
\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot
\code{LOW} & switch to \code{NEAREST\_AVAILABLE} if not already active \\
\code{MEDIUM} & keep the current strategy and alert the operator \\
\code{HIGH} & switch to \code{MINIMUM\_ETA} if not already active \\
\end{longtable}
\noindent
The \code{MEDIUM} level acts as a dead band: it never causes a strategy
switch and prevents oscillations between the two allocation policies.
When \code{enableAuto()} is invoked, the system immediately re-evaluates
the last observed traffic level using the same rule. If the level is
\code{MEDIUM}, the currently active strategy is retained.
\hypertarget{dynamic-fleet-rebalancing}{%
\subsubsection{\texorpdfstring{Dynamic fleet rebalancing}{Dynamic fleet rebalancing}}
\label{dynamic-fleet-rebalancing}}

\noindent
\textbf{Realised rebalancing cycle {[}v1.5{]}.}
The rebalancing planning cycle reads historical demand samples and active
events from the persistence layer and selects eligible idle robotaxis for
repositioning. It does not invoke \code{getDemandData()}: demand
information is obtained through \code{IPersistenceService}. Traffic data is
not used by this process, since it only affects the allocation strategy
managed by the \code{ModeController}.
For each selected robotaxi, the system requests the
\code{REBALANCING} transition, records the rebalancing action, and sends a
route command through \code{ExternalServicesGateway}. The command returns
route information, such as distance and duration.
\textbf{{[}v1.8{]}}
The completion of an ongoing repositioning is handled by a separate
telemetry cycle, independently of the ten-minute demand-planning cycle.
\code{RebalancingScheduler.completeArrivedVehicles()} reads fleet
telemetry and invokes \code{completeArrivedRebalancing()} for vehicles that
have reached their target zone. The operation asks \code{FleetMonitor} to
complete the transition to \code{AVAILABLE} and update the vehicle's
recorded zone.

\subsubsection{\texorpdfstring{Advance booking flow}{Advance booking flow}}

\noindent
\textbf{Booking candidate selection {[}v1.2{]}.}
Advance bookings use \code{getBookableRobotaxis()}, which considers
vehicles that may become available before the scheduled pickup time.
The subsequent \code{filterAvailable()} operation checks the selected
time window and excludes vehicles with conflicting reservations.
Robotaxis in \code{MAINTENANCE} are excluded because their return to
service cannot be predicted.

\hypertarget{the-reservation-timeline-v1.1}{%
\subsubsection{\texorpdfstring{The reservation timeline
\textbf{{[}v1.1{]}}}{The reservation timeline {[}v1.1{]}}}\label{the-reservation-timeline-v1.1}}

Immediate rides and advance bookings use the same reservation timeline.
Every assignment reserves a bounded interval, allowing the persistence
layer to prevent overlapping commitments for the same robotaxi.
For an immediate ride, the interval starts when the vehicle is assigned
and covers the estimated pickup and ride durations. For an advance
booking, it starts at the activation time before the scheduled pickup
and extends until the estimated end of the ride. A configurable buffer
is added to both intervals.
When a ride is completed or cancelled, the unused portion of its
reservation is released.

\hypertarget{advance-booking-activation-v1.1}{%
\subsubsection{\texorpdfstring{Advance booking activation
\textbf{{[}v1.1{]}}}{Advance booking activation {[}v1.1{]}}}\label{advance-booking-activation-v1.1}}

Advance bookings are activated shortly before their scheduled pickup
time by a periodically invocation of\code{AdvanceBookingActivator.runOnce()}, owned by the
\code{RideRequestManager}.
For each due booking, the system verifies whether the reserved robotaxi
is still eligible. If so, it is assigned to the ride and the normal
ride lifecycle begins. Otherwise, the system selects another eligible
vehicle through \code{AllocationManager.allocate()}. If no suitable
robotaxi is available, the booking is rejected and the Passenger is
notified.

\ddfigurestar{diagrams/sequence_diagrams/advance_booking_activation}{Advance booking activation [v1.1].}

\hypertarget{cancellation-v1.1}{%
\subsubsection{\texorpdfstring{Cancellation
\textbf{{[}v1.1{]}}}{Cancellation {[}v1.1{]}}}\label{cancellation-v1.1}}

The Passenger can cancel a ride request before the ride begins.
\code{RideRequestManager.cancel()} first verifies that the request belongs
to the Passenger and is still cancellable.
If the request has no assigned robotaxi, as in an advance booking that has
not yet been activated, no route is revoked and no vehicle assignment is
released. The active reservation is released through
\code{PersistenceManager}, while the booking record is closed by setting
its \code{closedAt} timestamp and clearing its reservation reference.
If a robotaxi has already been assigned and its current state allows
cancellation, the system first revokes its route through
\code{ExternalServicesGateway} and then asks \code{FleetMonitor} to release
the assignment and return the vehicle to \code{AVAILABLE}. The request is
then marked as \code{CANCELLED}, its reservation is released, and the
corresponding \code{Ride} is updated and the Passenger is notified.
Booking and reservation records are therefore retained for historical
purposes rather than deleted. A booking is closed and its reservation is
released, making the corresponding time window available again.
If the cancellation is not allowed in the current robotaxi state, the
request, booking, and reservation remain unchanged, and the Passenger
receives a rejection notification.

\hypertarget{selected-architectural-styles-and-patterns}{%
\section{Selected architectural styles and
patterns}\label{selected-architectural-styles-and-patterns}}

The following patterns are used to structure the main parts of the ROAd
system and to keep the implementation modular and extensible.

\subsection{Strategy - allocation algorithms}
\textbf{Problem.}
The system must support different robotaxi allocation policies depending
on traffic conditions or operator preferences. The selected policy must
be replaceable without modifying the ride-request logic.\\
\textbf{Solution.}
The abstract \code{AllocationStrategy} defines the
\code{selectRobotaxi()} operation. The concrete
\code{NearestAvailableStrategy} and \code{MinimumETAStrategy}
implement the available policies. The \code{AllocationManager} acts as
the context and maintains the registered strategies, selecting the
active one through its \code{StrategyName}. The
\code{ModeController} changes the active strategy when required by the
traffic level or by the operator, as shown in
Figure~\ref{fig:class_allocation}.\\
\textbf{Why.}
The Strategy pattern makes allocation policies interchangeable and
independently testable. It also allows additional strategies to be
introduced without changing the request-handling logic.

\subsection{Observer - state-change notifications}

\textbf{Problem.}
Passengers and fleet operators must receive updates when a robotaxi
changes state or a ride changes status. The domain objects should not
depend directly on client sessions or communication protocols.\\
\textbf{Solution.}
\code{Robotaxi} and \code{Ride} act as subjects, while
\code{NotificationManager} acts as the observer, as shown in Figure~\ref{fig:class_notification}. It receives domain
events and dispatches them to the connected
\code{PassengerAppSession} and \code{OperatorDashboardSession} objects.
Passenger sessions receive events related to their own rides, whereas
operator sessions receive fleet-wide events.\\
\textbf{Why.}
The Observer pattern decouples event producers from notification
recipients and supports dynamic client connections. Notifications are
sent after the corresponding state or status change has been persisted.

\subsection{State - robotaxi lifecycle}

\textbf{Problem.}
A robotaxi can perform different operations depending on its current
lifecycle state, and only specific transitions are valid from each
state. Distributing these rules across conditional statements could
lead to invalid state changes.\\
\textbf{Solution.}
The \code{Robotaxi} object delegates lifecycle operations to its current
\code{RobotaxiState}. The concrete states are
\code{AvailableState}, \code{AssignedState}, \code{ArrivingState},
\code{ArrivedState}, \code{InRideState}, \code{RebalancingState}, and
\code{MaintenanceState}. Invalid operations raise an
\code{IllegalTransitionError}. The complete lifecycle is shown in
Figure~\ref{fig:state_robotaxi}.

\ddfigure{diagrams/finite_state_machine/fsm_robotaxi_state}
{Design-level state machine of the Robotaxi realised through the State
pattern.}
{fig:state_robotaxi}
\noindent
\textbf{Why.}
The State pattern is used because the operations permitted on a
robotaxi depend directly on its current lifecycle state. Encapsulating
the valid transitions in separate state classes avoids a large
centralised conditional structure and prevents illegal operations by
construction, as shown in Figure~\ref{fig:class_state}. It also localises future changes to the affected state,
while keeping the \code{Robotaxi} context independent of
state-specific behaviour. This makes the lifecycle explicit, testable,
and consistent with the persisted state.

\subsection{Other patterns and styles}

\textbf{Problem.}
The system interacts with external providers and must support different
client interfaces without exposing provider-specific details to the
business logic. The frontend must also separate data management,
presentation, and user interaction responsibilities.\\
\textbf{Solution.}
The \code{ExternalServicesGateway} combines the
\textbf{Facade} and \textbf{Adapter} patterns to provide a uniform
interface to mapping, traffic, routing, telemetry, and vehicle services.
Provider-specific protocols are therefore isolated from the backend
components.\\
The passenger and operator clients are implemented with React and follow
the \textbf{MVC} principle by separating observable application state, rendered
views, and user-interaction logic. This represents a separation of
responsibilities in the frontend rather than a strict hierarchy of
MVC classes.\\
Backend services are created through \textbf{dependency injection}, with
one instance of each service per backend process where required by the
implementation. This provides process-local behaviour similar to the
Singleton pattern, without introducing a separate Singleton implementation.\\
\textbf{Why.}
These styles isolate external dependencies, keep the core logic
independent of provider-specific protocols, and separate frontend
responsibilities. They also simplify the evolution and testing of both
the clients and the backend services.

\textbf{R1 - Registration and Login}
&
\code{AuthenticationManager} manages passenger registration and user
authentication, stores account data through \code{PersistenceManager},
and issues signed access tokens. The API Gateway applies authentication

\\

\textbf{R2 - Profile Management}
&
The passenger and operator interfaces allow users to edit their own
profile. \code{AuthenticationManager.updateProfile()} validates and
persists the changes through \code{PersistenceManager}.
\\

\textbf{R3 - Immediate Ride Request}
&
\code{RideRequestManager} validates the request, obtains eligible
vehicles from \code{FleetMonitor}, and delegates selection to
\code{AllocationManager}. The assignment and its reservation are
recorded, and the passenger receives the result. Requests that cannot
be served are rejected.
\\

\textbf{R4 - Advance Booking}
&
\code{FleetMonitor} identifies bookable vehicles, and
\code{PersistenceManager} filters them against the requested time
interval. \code{AllocationManager} selects a candidate, while
\code{PersistenceManager} atomically stores the booking and reservation.
\code{AdvanceBookingActivator} subsequently revalidates availability
and activates the booking, attempting reallocation when necessary.
\\

\textbf{R5 - Automated Vehicle Allocation}
&
\code{FleetMonitor} identifies vehicles eligible according to their
operational state, while reservation checks exclude conflicting
commitments. \code{AllocationManager} delegates selection to the
globally active \code{AllocationStrategy}, using distance or estimated
arrival time and external routing information where needed.
\\

\textbf{R6 - Ride Status Notifications}
&
\code{Robotaxi} and \code{Ride} act as Subjects in the Observer pattern.
After changes are persisted, \code{NotificationManager} delivers
passenger notifications through the WebSocket channel, covering
vehicle assignment, estimated arrival time, pickup arrival, and ride
completion. Arrival estimates use information obtained through
\code{ExternalServicesGateway}.
\\

\textbf{R7 - Fleet Monitoring}
&
The telemetry service obtains vehicle observations through
\code{ExternalServicesGateway}, and \code{FleetMonitor} records
positions and maintains the fleet state. The Operator Dashboard combines
periodic position updates with pushed state-change events to update
its map and fleet status bar.
\\

\textbf{R8 - Runtime Strategy Selection}
&
The Operator Dashboard exposes controls for selecting Nearest Available
Vehicle or Minimum ETA. Through \code{ModeController} and
\code{AllocationManager}, the selected strategy becomes the globally
active policy for subsequent allocations without interrupting the
service.
\\

\textbf{R9 - Maintenance Management}
&
\code{MaintenanceManager} validates maintenance operations through the
robotaxi State pattern and persists the maintenance record and vehicle
state. Vehicles in \code{MAINTENANCE} are excluded from allocation and
booking candidates until maintenance is completed.
\\

\textbf{R10 - Demand Analysis}
&
\code{RebalancingManager} reads historical demand samples and active
events through \code{PersistenceManager}. It estimates demand for each
zone and compares it with available vehicle supply to identify
deficits and surpluses.
\\

\textbf{R11 - Proactive Fleet Rebalancing}
&
\code{RebalancingManager} selects eligible idle vehicles from surplus
zones and directs them toward zones with unmet demand, preserving
existing commitments. \code{ExternalServicesGateway} issues movement
commands, while \code{FleetMonitor} manages lifecycle transitions.
A separate telemetry-driven cycle completes arrived repositionings.
Rebalancing operates independently of allocation Auto/Manual mode.
\\

\textbf{R12 - Auto Mode (Default)}
&
The initial configuration uses Auto Mode and Nearest Available Vehicle.
\code{TrafficMonitor} reads the service-area traffic level through
\code{ExternalServicesGateway} and invokes \code{ModeController}.
At Low, the controller selects Nearest Available Vehicle; at High,
Minimum ETA. At Medium, it retains the active strategy and alerts the
operator with a suggestion to use Minimum ETA.
\\

\textbf{R13 - Manual Mode (Override)}
&
An operator strategy selection causes \code{AllocationManager} to
persist the selected strategy and Manual Mode atomically.
Traffic changes cannot alter that selection until the operator
explicitly re-enables Auto Mode. \code{ModeController} then immediately
re-evaluates traffic: Low selects Nearest Available Vehicle, High selects
Minimum ETA, and Medium retains the current strategy.
\\


\textbf{R14 - Ride Cancellation}
&
\code{RideRequestManager} marks the request as cancelled and releases
its reservation, making the interval available again. For an assigned
vehicle, pickup navigation is revoked through
\code{ExternalServicesGateway}, and \code{FleetMonitor} returns the
vehicle to \code{AVAILABLE}. Cancellation is supported during
assignment, approach, and waiting at pickup, but is rejected once the
ride begins. An unactivated booking requires no vehicle-state change.
\\

\textbf{NFR1 - Concurrency Handling}
&
Database transactions, conditional vehicle-state updates, and
reservation constraints coordinate concurrent ride requests and
vehicle-data updates. These mechanisms preserve non-overlapping
commitments and valid lifecycle transitions when operations compete
for the same vehicle.
\\

\textbf{NFR2 - Automatic Update Delivery}
&
The Observer pattern and WebSocket channel deliver relevant persisted
state changes to connected Passenger and Fleet Operator interfaces.
The clients update their views automatically, without requiring a
manual refresh. Vehicle positions are refreshed separately through
periodic requests.
\\

\textbf{NFR3 - Scalability}
&
The domain logic operates on persisted collections of passengers and
robotaxis rather than a fixed population. Separating clients, business
logic, and persistence allows these populations to grow without
changing domain rules. Backend replication is an architectural
extension; the prototype uses one instance with local simulator and
WebSocket-session state.
\\

\textbf{NFR5 - State Consistency}
&
\code{Robotaxi} delegates lifecycle operations to its current
\code{RobotaxiState}. Inadmissible operations raise
\code{IllegalTransitionError} without applying the requested transition.
Conditional persistence checks also reject updates based on a state
that has changed concurrently.
\\

\textbf{NFR6 - Interface Clarity}
&
The clients use explicit labels and visual indicators to distinguish
ride states, vehicle states, allocation strategies, and control modes.
Confirmation messages and error feedback indicate whether user
actions succeeded or were rejected.
\\

\textbf{NFR7 - Extensibility of Allocation Logic}
&
Allocation policies implement the common \code{AllocationStrategy}
interface and are registered with \code{AllocationManager}.
\code{RideRequestManager} delegates allocation through the same service
interface, so adding a policy does not require changing its core
request-management logic.
\\

\textbf{NFR8 - Separation of Concerns}
&
Account, ride, and fleet management are assigned to distinct components
with explicit service interfaces. \code{ExternalServicesGateway} uses
Facade and Adapter to isolate backend provider integrations, allowing
them to change without modifying unrelated domain logic.
\\

\textbf{NFR9 - Stability of Auto-Switching}
&
\code{ModeController} retains Minimum ETA when traffic falls from High
to Medium after an automatic switch. Automatic reversion to Nearest
Available Vehicle occurs only at Low, implementing the hysteresis
required by R12.
\\

\textbf{NFR10 - Consistency of Manual Override}
&
The selected strategy and the transition to Manual Mode are persisted
atomically. Automatic strategy updates are conditional on Auto Mode
still being active, preventing a concurrent traffic evaluation from
overwriting a manual selection once Manual Mode has taken effect.
\\

\section{Implementation and Integration Order}
\label{implementation-and-integration-order}

Integration proceeds incrementally, starting from shared infrastructure
and progressing toward complete user workflows, following the \textbf{bottom-up methodology}. Component interfaces
and test doubles allow individual modules to be developed before all
their collaborators are available. Concrete dependencies are then
integrated and checked through the corresponding milestone tests.

\begin{enumerate}
    \item \textbf{Shared infrastructure and persistence.}
    Define shared types, API schemas, component ports, and the database
    schema. Integrate \code{PersistenceManager}, including transactions
    and reservation constraints.

    \item \textbf{Authentication and API access.}
    Integrate \code{AuthenticationManager} with persistence and the API
    Gateway, covering registration, login, profile updates, and
    role-based access control.

    \item \textbf{Vehicle lifecycle and maintenance.}
    Implement \code{Robotaxi} and its State classes, then integrate
    \code{FleetMonitor} and \code{MaintenanceManager} with persistence.
    Verify admissible transitions and vehicle eligibility.

    \item \textbf{Allocation strategies.}
    Implement \code{AllocationManager} and its strategies using supplied
    candidate lists and an external-service test double.
    Integrate persistent strategy selection.
    \code{RideRequestManager}, rather than \code{AllocationManager},
    coordinates candidate retrieval from \code{FleetMonitor}.

    \item \textbf{Ride requests and reservations.}
    Integrate immediate requests, advance bookings, atomic reservations,
    cancellation, and booking activation. Verify reallocation when a
    reserved vehicle is no longer eligible.

    \item \textbf{Ride lifecycle and notifications.}
    Integrate ride-status persistence, lifecycle operations, and the
    Observer notification mechanism. Connect
    \code{NotificationManager} to authenticated WebSocket sessions.

    \item \textbf{Strategy control and rebalancing.}
    Integrate \code{ModeController}, \code{TrafficMonitor}, and
    \code{RebalancingManager}. Cover hysteresis, manual override,
    demand estimation, and automatic repositioning.
    Demand samples and events are read from the database.

    \item \textbf{External adapters and fleet simulation.}
    Integrate the routing and traffic adapters and the fleet simulator
    through \code{ExternalServicesGateway}. Connect telemetry to ride
    progression and rebalancing completion, and verify routing fallback
    behaviour.

    \item \textbf{Clients and complete workflows.}
    Integrate the Passenger Application and Operator Dashboard with
    the HTTP and WebSocket interfaces. Verify the main user workflows
    through browser tests and complete RASD scenario tests.
\end{enumerate}

\section{Testing Strategy}
\label{testing-strategy}

Verification follows a \textbf{V-model approach}, relating testing
activities to the specifications and design elements they verify.
Unit tests check individual behaviours against the detailed design,
integration tests verify component interactions and interface
contracts, and system tests assess complete workflows against the
RASD requirements. Browser tests additionally verify these workflows
through the user interfaces. Architecture and contract checks
complement the behavioural tests.
\begin{figure}[H]
    \centering
    \includegraphics[
        width=\textwidth,
        height=0.5\textheight,
        keepaspectratio
    ]{images/v_model_verification_levels.png}
    \caption{V-model approach}
\end{figure}
\begin{description}

    \item[\textbf{Unit testing.}]
    Unit tests verify individual classes and functions in isolation,
    substituting their dependencies where necessary. They cover
    allocation strategies, robotaxi states, ride management, booking
    activation, telemetry processing, notifications, and access control.

    Allocation tests exercise empty and unsuitable candidate sets,
    feasible selections, and deterministic tie-breaking. State tests
    check admissible operations and the rejection of illegal
    transitions. Additional tests cover geographical calculations,
    simulated movement, and client-side presentation logic, including
    ride phases, traffic indicators, and alert classification.

    \item[\textbf{Integration testing.}]
    Integration tests verify that collaborating components exchange
    information correctly and preserve system consistency. They cover
    authentication, persistence, fleet management, allocation, ride
    management, notifications, mode control, and rebalancing.

    Database-backed tests use isolated PostgreSQL instances to check
    reservation conflicts, transaction rollback, concurrent updates,
    and state reconstruction. External-adapter tests exercise the
    concrete gateway against a controlled HTTP provider implementing
    the expected OSRM protocol. These tests cover routing responses,
    caching, malformed responses, provider unavailability, and fallback
    estimates.

    \item[\textbf{Architecture and contract testing.}]
    Architecture checks verify module boundaries and the exposure of
    declared service ports. Contract tests compare the generated
    OpenAPI specification with the stored API contract, detecting
    unintended changes to the interfaces used by clients.

    \item[\textbf{Milestone verification.}]
    A milestone is an incremental development checkpoint with a
    defined set of capabilities and completion criteria. Its
    verification combines behavioural, integration, and structural
    checks to establish that the increment is ready to support
    subsequent development. Milestones organise progress across
    testing levels rather than introducing a separate testing level.

    The project uses the following milestones:

    \begin{itemize}
        \item \textbf{M0 -- Application Skeleton.}
        Establish the backend and client applications, basic
        connectivity, and the automated verification infrastructure.

        \item \textbf{M1 -- Persistence and Database Schema.}
        Verify data storage, availability filtering, and reservation
        constraints, including competing reservations for the same
        robotaxi.

        \item \textbf{M1b -- Authentication and Accounts.}
        Verify registration, login, profile updates, role-based access,
        and protection of account credentials.

        \item \textbf{M2 -- Fleet Lifecycle and Maintenance.}
        Verify the robotaxi State pattern, persistence and
        reconstruction of vehicle state, maintenance operations,
        and allocation eligibility.

        \item \textbf{M3 -- Allocation Strategies.}
        Verify vehicle selection under both strategies, runtime policy
        changes, tie-breaking, and the registration of an additional
        test strategy.

        \item \textbf{M4 -- Ride Requests and Bookings.}
        Verify immediate assignments, atomic advance reservations,
        cancellation and reservation release, and booking activation
        with reallocation when necessary.

        \item \textbf{M5 -- Ride Notifications.}
        Verify ride-status progression and authenticated WebSocket
        delivery, including passenger-specific events, fleet-wide
        operator events, and subscription cleanup on disconnection.

        \item \textbf{M6 -- Strategy Control and Rebalancing.}
        Verify traffic hysteresis, manual override, reactivation of
        Auto Mode, demand estimation from known data, and automatic
        dispatch of vehicles from surplus zones.

        \item \textbf{M7 -- External Adapters and Fleet Simulation.}
        Verify routing and telemetry integration, fallback behaviour,
        simulated vehicle movement, and rebalancing completion.
        Cancellation checks also cover route revocation while the
        vehicle is approaching or waiting at pickup.

        \item \textbf{M8 -- User Interfaces.}
        Verify passenger and operator workflows through the browser,
        including ride-status updates and manual strategy selection.

        \item \textbf{M9 -- Complete Scenarios and Demonstration.}
        Verify the four RASD scenarios, concurrent requests for the
        last eligible vehicle, requirement-to-test traceability, and
        readiness of the installation and demonstration procedures.
    \end{itemize}

Milestone checks provide an additional verification stage before system
testing. Although not a separate testing level in the classical V-model,
they combine checks from different levels to assess the completeness
and consistency of each implementation increment.They are retained as regression tests and extended
    when later increments expand previously introduced behaviour.

    \item[\textbf{System scenarios and browser testing.}]
    System scenarios exercise the four RASD workflows: immediate
    rides, advance bookings, automatic/manual strategy management,
    and fleet rebalancing. They check that the integrated components
    produce the expected outcomes across complete sequences of
    operations.

    Browser tests complement these scenarios by exercising the actual
    interfaces. They cover client connectivity, passenger ride tracking,
    advance booking and cancellation, profile updates, operator
    strategy controls, fleet monitoring, and maintenance.

    A passenger browser test also checks that the ride-request
    workflow can be completed in four interactions under its defined
    initial conditions. This is an additional usability check,
    rather than a constraint imposed by NFR6.

    \item[\textbf{Acceptance walkthrough.}]
    The final demonstration presents representative passenger and
    operator workflows and relates their observable outcomes to the
    RASD goals. This walkthrough complements the automated checks
    with a review of the system from the users' perspective.

\end{description}

\textbf{NFR8 - Separation of Concerns}
&
Architecture review and module-boundary tests check distinct component
responsibilities. External-service integration tests exercise adapters
independently using controlled provider responses, while domain tests
substitute service ports. These checks support changing backend
integrations without modifying unrelated domain logic.
\\

\textbf{NFR9 - Stability of Auto-Switching}
&
Starting in Auto Mode with Nearest Available Vehicle, the sequence
Low-Medium-High-Medium-Low must switch strategy only at High and
at the final Low. Mode integration and milestone tests also verify
that Medium retains the current strategy and generates the appropriate
operator alert.
\\

\textbf{NFR10 - Consistency of Manual Override}
&
Manual strategy selection and the transition to Manual Mode must be
atomic. Mode integration tests check that a stale automatic evaluation
cannot overwrite the manual selection, and that subsequent traffic
observations leave it unchanged until Auto Mode is explicitly restored.
\\
